- **Proposed approach:** Profile with `python -X importtime -c "import cyber_tools"` to find the dominant contributor, then move that import (or module-level initialization) behind a function/lazy accessor. Must not change any tool's behavior.
- **Dependencies:** None (internal to cyber_tools.py), but it is a 136KB core module imported almost everywhere.
- **Estimated complexity:** Medium — the edit is small once the culprit is found, but the blast radius is the whole suite.
- **Testing approach:** Full suite green + a focused assertion that `import cyber_tools` completes under a budget (e.g. <10s) in a fresh process.

- **Status:** 🧊 deferred (post-deadline) — **profiled 2026-10-05.** Root cause pinned via `python -X importtime`: `cyber_tools` → `key_manager` (17.5s cumulative) → eager top-level SDK imports in **`key_manager.py` lines 86–101**: `from openai import OpenAI as _OpenAI` (≈12.8s — `openai` building its full `openai.types` tree dominates) and `from google import genai` + `google.genai.{errors,types}` (≈4.6s). `cyber_tools`' own top-level imports are light; essentially the entire cost is these two SDKs. ## 10. Multi-channel inbound messaging bridge (Discord / Telegram / WhatsApp / SMS → STAI agent)
- **Idea:** Let the owner message the SVS-Cyber/STAI SOC agent from everyday chat apps (Discord, Telegram, WhatsApp, SMS) and get replies in the same channel — **on-call / mobile triage** without the desktop UI.
- **Why it belongs (mission):** An on-call defender often isn't at the UI. Directing the SOC agent by chat is operator ergonomics for the existing defensive workflow — not a new mission; it reuses the same agent, approvals, and safety gating.
- **Problem it solves:** STAI is reachable only via the Next.js UI / local API (`POST /api/chat`); the owner wants it from anywhere.
- **Findings (owner-requested research, 2026-10-05):** OpenClaw (`openclaw/openclaw`, TypeScript pnpm monorepo) ships channel **plugin extensions** at `extensions/<channel>/`. Confirmed: `discord`, `telegram`, `whatsapp` (QR login), `sms`, plus `slack`, `signal`, `imessage`, `matrix`, `msteams`, `googlechat`, `line`, `irc`, `feishu`, `mattermost`, `nextcloud-talk`, `synology-chat`, `nostr`. Each follows a shared plugin contract (`openclaw.plugin.json`, `channel-plugin-api.ts`, `channel-config-api.ts`, `runtime-api.ts`, `secret-contract-api.ts`, `allow-from.ts`, `setup-entry.ts`) and depends on OpenClaw's `gateway-protocol`/`gateway-client`. **They are TypeScript plugins, not standalone libs, and STAI's backend is Python** (`cyber_os`, `cyber_agent.py`, `ui/api_server.py`) — so OpenClaw's code cannot be pasted in; use it as the *reference* for inbound-event shape, session-key mapping, and allow-lists.
- **Universal seam:** STAI's agent is already an HTTP API — `POST /api/chat` (`ui/api_server.py:166`; body `{message, session_id, model?}` → `{status, message, …}`), approvals at `/api/approval/{id}/respond`, `/api/agent/approve`, `/api/agent/cancel`, live events on `/ws`. Every adapter normalizes an inbound message and POSTs there, relaying the reply — reusing all existing safety/agent logic unchanged.
- **Approach (staged):** **Phase 1 (offline):** the provider-agnostic seam — a normalized `InboundMessage(channel, sender_id, text, thread_id)`, a **default-deny** sender allow-list, thread→`session_id` mapping, forwarding via a `ChatClient`, reply relay, and a `MockChannelAdapter` — plus offline unit tests. **Phase 2+ (owner-secrets-gated):** thin per-channel adapters (Telegram first — free, simplest API; then Discord; then SMS via Twilio; WhatsApp last). **Option A** (front STAI with OpenClaw's gateway — reuses its channel code but adds a whole TS runtime + cross-language bridge) is documented but NOT recommended pre-deadline.
- **Dependencies:** Phase 1 — none (stdlib only). Phase 2+ — one lib per channel (`python-telegram-bot` / `discord.py`) + a Twilio account (SMS) / WhatsApp Cloud API.
- **Secrets (owner-provided; gitignored, never logged):** Discord bot token; Telegram bot token; Twilio Account SID + Auth Token + number; WhatsApp Cloud API token + phone-number id + verify token.
- **Security (inbound command channel into a cyber agent — inbound text is UNTRUSTED):** default-deny allow-list; reuse STAI's existing approval gating (no tool auto-executes); per-sender rate limiting; reject non-text/oversized payloads; keep tokens out of logs/audit; watch for prompt-injection via inbound text.
- **Estimated complexity:** Phase 1 low; whole feature Medium–High.
- **Testing approach:** Phase 1 offline — unit tests for normalization, default-deny allow-list (exact + wildcard), session-id mapping, forwarding to a fake client, and reply relay (no network/secrets). Phase 2+ manual verification with a throwaway token + platform-SDK-mocked integration test.
- **Safe to implement automatically:** **Phase 1 YES** (offline seam). Phase 2+ NO (needs owner secrets + sign-off). Never auto-run Option A.
- **Status:** 🛠️ Phase 1 in progress (2026-10-06) — see the Implemented log.

## 11. Harden the messaging-bridge seam further (strict allow-list ids + inbound payload guards)
- **Idea:** Two small, security-relevant hardenings of the Phase-1 bridge seam, surfaced by the 2026-10-08 `AllowList` review:
  - **(a) Strict allow-list id validation / fail-loud option:** the bare-string footgun is fixed (coerced to one id, 2026-10-08), but a non-string id (`[123]`, `[None]`) or an empty id still passes `frozenset(...)` silently. It fails *safe* (an exact string `sender_id` never matches a non-string member ⇒ deny), so it is not a hole — but it is a silent misconfig. Option: validate at construction that every id is a non-empty `str`, raising on anything else (fail-loud is a stronger posture for a security boundary than silent acceptance).
  - **(b) Inbound payload guards at the chokepoint:** `MessageBridge.handle` forwards `inbound.text` to the agent unconditionally. Idea #10's security section explicitly requires "reject non-text/oversized payloads." Add a max-length + non-empty/str guard at the single seam before the agent is invoked.
- **Problem it solves:** Defense-in-depth for an UNTRUSTED inbound command channel into a cyber agent — catches operator misconfig loudly (a) and bounds adversarial payload size/shape at one chokepoint (b), before any live channel (Phase 2) is wired in.
- **Dependencies:** None (internal to `stai_messaging/bridge.py`); stdlib only.
- **Estimated complexity:** Low each.
- **Testing approach:** Pure offline unit tests — (a) assert construction raises on a non-str/empty id and still accepts str lists + the bare-string single-id form; (b) assert oversized/empty/non-str text is refused (dropped or `ValueError`) and the agent is never invoked, while normal text still round-trips.
- **Safe to implement automatically:** **Partial.** (a) and (b) both touch the bridge, but the seam is still offline (zero live blast radius). They are deferred not for risk but because each embeds a **policy choice** the owner should set: fail-loud vs. coerce for (a); the max payload size and refuse-vs-truncate behavior for (b). Record the policy, then implement with tests — do not guess the limit autonomously.
- **Status:** 💡 proposed (2026-10-08) — needs an owner policy decision on strictness + max payload size; the correctness/footgun half of (a) is already shipped.
