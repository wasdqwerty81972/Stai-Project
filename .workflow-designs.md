=== THE DESIGN ===

1. PRESET REGISTRY (data, not tools) — new module, e.g. cyber_os/command_presets.py. One entry per collapsed wrapper:
   {id, summary, env, argv_template, risk_level, requires_admin, probe_binary, fallback_preset, example}

2. ONE STARTUP PROBE, CACHED NEXT TO wsl_state.
   - cross_platform / native_windows: shutil.which(probe_binary).

3. EXTEND shell_exec — DO NOT ADD A NEW TOOL.

   - freeform (no preset): keeps MODIFIES_SYSTEM and the existing gate.

4. SYSTEM PROMPT SECTION — generated, not hand-written. ## RECOMMENDATION

## The failure to prevent, stated precisely

`GuardrailManager.request_approval` (`D:\STAI 2\cyber_tools.py:140`) is:

```python
if risk_level == RiskLevel.READ_ONLY and self.auto_approve_read_only:
    return True
```

READ_ONLY is the only tier that skips the human, and `auto_approve_read_only` defaults True. `CyberAgent._wait_for_approval` (`D:\STAI 2\cyber_agent.py:909`) duplicates the same shortcut. So the concrete failure is: `nmap 10.0.0.1; rm -rf /` classified READ_ONLY because the classifier looked at the prefix — it executes with no prompt, and the audit line says `auto_approved / read_only`.

The symmetric failure matters too. `Tools_cyber/shell_exec.py:45` pins `risk_level = RiskLevel.MODIFIES_SYSTEM` as a class attribute, copied into a `ToolDefinition` at registration (`cyber_tools.py:2473-2489`). If the unified tool does that, every `ping`, `Get-Process` and `nmap` — 59 wrappers' worth of previously-silent read-only traffic — raises an approval card. Operators rubber-stamp, and the audit log then falsely records "operator approved" for the one genuinely destructive command. A single static risk level is wrong in both directions.

## Design: risk becomes a function of the resolved command, not a field on the tool

### 1. `classify_command(command: str, interpreter: str) -> CommandRisk`

```python
@dataclass(frozen=True)
class CommandRisk:
    level: RiskLevel            # existing enum, cyber_tools.py:56
    requires_admin: bool
    reason: str                 # operator-facing sentence for the approval card
    matched_rules: List[str]    # rule ids, for audit
    segments: List[str]         # every decomposed segment considered
    undecidable: List[str]      # segments no rule covered
    confidence: str             # "exact" | "no_rule" | "unparseable"
    ruleset_hash: str
```

### 2. Four classification principles

**Classify every segment, take the maximum — never the prefix.** Split first, classify all parts, `level = max(levels)`, `requires_admin = any(...)`. A benign prefix cannot lower the verdict because the prefix is never the unit of classification.

**Unknown floors at MODIFIES_SYSTEM, never READ_ONLY.** READ_ONLY must be *earned* by an explicit allowlist entry; it is never a default and never inferred. The asymmetry decides the direction: a false MODIFIES_SYSTEM costs one click; a false READ_ONLY runs `Remove-Item -Recurse` unattended.

**Unparseable escalates to DESTRUCTIVE, not to the middle tier.** If the splitter cannot decompose the string (shlex raises, unbalanced quotes, nesting past depth N, control characters), we have positive evidence the string is doing something the parser was not built for. That is evidence of evasion, not of benignity.

**Match on argv, not substrings.** `execute_system_command` already contains the anti-pattern to avoid — `cyber_tools.py:1097` does `any(op in cmd_lower for op in ["rm ", "del ", ...])`, which misses `rm\t`, `"rm"`, `/bin/rm`, `Remove-Item` and false-positives on `--form `. Instead: `tokens = ApprovalEngine.tokenize_command(segment)`, normalize `tokens[0]` (basename, strip `.exe`, casefold), exact-key lookup.

### 3. Per-interpreter splitters with an explicit refuse-list

`execute_system_command` (`cyber_tools.py:1104-1112`) spawns three different grammars — `cmd.exe /c`, `powershell.exe -Command`, `wsl.exe bash -c` — so one splitter cannot be correct for all three. Each gets its own separator set (bash `; && || | & \n $() `` <()`; cmd `& && || | ^ %VAR% for /f call`; PowerShell `; | && || & $() backtick`).

Each splitter carries a list of constructs it **refuses to reason about**. Presence of any one pins the whole command to DESTRUCTIVE regardless of the rest: `eval`, `iex` / `Invoke-Expression`, `powershell -e/-enc/-EncodedCommand`, `bash -c`, `sh -c`, `cmd /c`, `certutil -decode`, `FromBase64String`, `curl … | sh`, `IWR … | iex`, nested `$(…)`/backticks past depth N.

This is the answer to "cannot be talked past." You do not out-parse an attacker inside a construct whose purpose is to hide the payload. `nmap 10.0.0.1 && $(echo cm0gLXJmIC8K | base64 -d | sh)` never needs its inner payload understood — `$(…)`, `base64 -d` and `| sh` each independently pin it.

**Encoded payloads:** attempt one decode pass (PowerShell `-EncodedCommand` base64/UTF-16LE, `certutil -decode`, `base64 -d` with a literal arg), classify the decoded text with the same classifier, take `max(outer, inner)` — but floor at MODIFIES_SYSTEM even if the decoded content is a pure allowlisted read, and never let a decode pass yield READ_ONLY. Decoding informs the operator ("this base64 expands to `Get-Process`"); it does not grant auto-approval, because the decoder and the real interpreter are different implementations and any disagreement must land in front of a human.

### 4. Two traps that survive correct splitting

**Argument-position execution.** `find . -exec rm {} \;`, `xargs rm`, `nmap --script=http-put`, `tar --checkpoint-action=exec=sh`, `git -c core.pager='sh -c …' log`, `ssh host 'rm -rf /'`. All argv-legal with an allowlisted `tokens[0]`. So a READ_ONLY rule is never "this binary is read-only" — it is "this binary is read-only **while its flags stay inside this set**." Each rule carries `allowed_flags`; any unrecognized flag on an allowlisted binary drops that segment to MODIFIES_SYSTEM. A new nmap flag prompts once instead of silently running `--script`.

**Redirection.** `nmap 10.0.0.1 > C:\Windows\System32\drivers\etc\hosts` is argv-clean and prefix-clean. Any `>` / `>>` / `Out-File` / `Set-Content` / `Tee-Object` with a target, or `-o/-oN/-oX/--output` on an allowlisted scanner, floors the segment at MODIFIES_SYSTEM — DESTRUCTIVE if the target resolves under a protected path. This is the real version of the substring check at `cyber_tools.py:1097`.

### 5. `requires_admin` — currently decorative, given consequence

Grep confirms `requires_admin` is enforced **nowhere**: it flows only into `to_manifest()` (`cyber_tools.py:265`), the plugin adapter (`:361`), and `cyber_os/nemo_agent_toolkit.py:42`. `execute_tool` never reads it. Derive it per-call from three ORed sources:

1. **Rule-declared** — `masscan`, `arp-scan`, `netdiscover`, `tcpdump`, `auditctl`, `sc config`, `netsh advfirewall set`, `Get-WinEvent -LogName Security`.
2. **Target-derived** — segment touches `HKLM:`, `%SystemRoot%\System32`, `/etc`, `/boot`, `/sys`, `C:\Windows`, service control, scheduled tasks, `/dev/`.
3. **Observed** — `KernelPrivilegeValidator.is_privileged()` (`cyber_tools.py:545`) for the current process.

Then two behavioural consequences. If `requires_admin and not is_privileged()`: surface in the card that the command will likely fail or partially apply, rather than letting it fail opaquely. If `requires_admin and is_privileged()`: **raise the floor one tier** (READ_ONLY→MODIFIES_SYSTEM, MODIFIES_SYSTEM→DESTRUCTIVE), because the identical command from an elevated process has a strictly larger blast radius.

### 6. Wiring — surgical, and it fixes a TOCTOU gap

`ToolDefinition` gains `risk_classifier: Optional[Callable[[Dict], CommandRisk]] = None`. All 148 python_func tools are untouched; `risk_level` stays authoritative when `risk_classifier is None`.

At `cyber_agent.py:1030`, when a classifier is present, call it and pass `risk.level` instead of `tool_def.risk_level`, merging `reason` / `matched_rules` / `segments` / `undecidable` into `guardrail_details` so the card shows *why*. Classify once; use that one value for both the gate and the audit event.

**Ordering must invert.** Today the guardrail runs at line 1030 against `args`, but the string that actually executes is built at line 1093 (`cmd_str = tool_def.command_template.format(**args)`) and wrapped at 1103-1108. Approval is granted against arguments; execution happens against a string assembled afterwards. With per-tool static risk that is merely odd. For a unified command tool it is the whole ballgame: build the final string first, classify *that exact string*, approve it, then pass the same string object forward to `execute_system_command` — never rebuild it post-approval.

### 7. Close the threat_score escape hatch for classified commands

`AutomatedGuardrailManager.request_approval` (`cyber_tools.py:537`) and `_wait_for_approval` (`cyber_agent.py:911`) auto-approve DESTRUCTIVE **and** KERNEL_INTERVENTION when `details["threat_score"] >= 8`. Defensible for `block_ip` or `terminate_process` — bounded, known semantics. Not defensible for an arbitrary command string: it means that during an active incident, when the agent is most likely acting on attacker-influenced input, an arbitrary command runs unattended. Gate that path on `tool_def.risk_classifier is None`, or equivalently cap auto-remediation at MODIFIES_SYSTEM and require rules to opt in with `auto_remediable: true`. A classification of `unparseable` or `no_rule` is never auto-remediable at any threat score.

### 8. Audit and extension

Rules live in data, not an if-chain: `cyber_os/policy/command_rules.yaml`, loaded and hash-recorded at startup. Per rule: `id`, `interpreter`, `match` (binary + flag constraints), `level`, `requires_admin`, `auto_remediable`, `rationale`, `owner`, `added`.

The loader **fails closed**: a malformed rules file means "no allowlist," therefore everything classifies MODIFIES_SYSTEM — degraded but safe. It must never mean "no rules, allow."

Every classification emits a `command_classified` audit event with command, interpreter, level, matched rule ids, segments, undecidable list and ruleset hash. Operators answer "why was this auto-approved?" from the log alone, and find over-broad rules by grouping. Repeated entries in `undecidable` are candidates for new rules — proposed and reviewed by a human, never auto-learned from observed traffic, since auto-learning an allowlist is exactly how an attacker installs their own rule.

Expose `classify_command` as a read-only introspection tool for dry-run: "what would this rate?" without executing.

### 9. The 59 wrappers ARE the seed allowlist

Each existing template's binary plus its literal flags becomes one rule, derived mechanically from the registrations at `cyber_tools.py:2125-2177+`: `nmap_scan` → `{binary: nmap, allowed_flags: [], level: read_only}`; `trivy_scan` → `{binary: trivy, required_subcommand: fs, level: read_only}`; `masscan_scan` → `{binary: masscan, allowed_flags: ["-p*"], level: read_only, requires_admin: true}`.

This preserves the exact per-tool signal the collapse would otherwise destroy, and makes the migration auditable — the diff is 59 rules reproducing 59 existing decisions. Regression test beside `tests/test_tool_registry_consistency.py`: for each retired wrapper assert its canonical expansion still classifies READ_ONLY, and assert the injected variant (`target="1.1.1.1; rm -rf /"`) classifies DESTRUCTIVE.

### 10. Reuse `ApprovalEngine` — it exists and is dead code

`cyber_os/approval_engine.py` already implements `tokenize_command` (shlex, `posix=False`), `DISALLOWED_PREFIX_CHARACTERS`, `is_prefix_rule_safe`, `has_shell_injection`, and argv-prefix session grants. It is imported at `cyber_agent.py:26` and instantiated at `:660` — and **never called from `execute_tool`**. The session-grant mechanism is exactly the right pressure valve for approval fatigue: an operator approves `nmap 10.0.0.1` once and grants the argv prefix `["nmap"]` for the session, with `is_prefix_rule_safe` already rejecting any prefix containing shell control characters. Wire `check_session_grant` in as a tier that can satisfy a MODIFIES_SYSTEM gate — but never one that can satisfy DESTRUCTIVE, `unparseable`, or a refuse-list hit.

## RATIONALE

Three alternatives were on the table.

**(a) Keep a static risk_level on the unified tool.** Rejected in both settings. READ_ONLY auto-approves arbitrary commands at `cyber_tools.py:141` — indefensible. MODIFIES_SYSTEM (what `shell_exec.py:45` does today) prompts on every `ping`, converting 59 tools of silent read-only traffic into approval cards; the predictable operator response is reflexive approval, which is auto-approval wearing an audit trail that lies. Static risk cannot express a property of a string that does not exist until call time.

**(b) LLM-based classification of the command.** Rejected as the gate. The input is attacker-influenceable by construction — this is a defensive-security agent reading hostile artifacts — so prompt injection targets the classifier directly, and the classifier's verdict is what decides whether a human sees the command. It is also non-deterministic and unauditable: "why was this auto-approved" has no answer you can put in a log or replay. It could reasonably enrich the operator-facing `reason` text; it must not produce `level`.

**(c) Denylist of dangerous patterns.** Rejected: it defaults to allow, so every gap is an auto-approved destructive command. `cyber_tools.py:1097` is a live demonstration — a substring denylist that misses `/bin/rm`, `Remove-Item`, `"rm"`, and tab-separated `rm`.

The chosen design is an **allowlist for READ_ONLY only**, with everything else defaulting into the human-visible tiers. This works because of the tier asymmetry in the existing code: READ_ONLY is the sole tier that bypasses the operator, so it is the only tier that needs to be provably earned. The other three all reach a human (once the threat_score hatch is closed for classified commands), so misclassification among them costs clicks, not integrity.

Segment-max over prefix-match is the specific countermeasure to the named failure. The refuse-list is the countermeasure to the thing allowlists cannot handle: constructs whose entire purpose is to make static analysis wrong. Refusing to reason about `eval`/`iex`/`-EncodedCommand`/`| sh` and classifying on *presence of the construct* is strictly stronger than trying to analyze inside them, and it is cheap and deterministic.

Seeding the ruleset from the 59 existing templates is what makes this shippable rather than aspirational: it is a mechanical derivation of decisions the codebase already encodes, so the collapse provably preserves the current risk posture instead of asking operators to trust a new classifier from day one.

## RISKS

- Approval volume rises for anything outside the seeded allowlist. That is the intended trade, but it is real. If operators respond by widening rules carelessly the allowlist rots into a rubber stamp — the exact failure a static MODIFIES_SYSTEM would have caused. Mitigated by per-rule owner/added-date, by reviewing which rules fire most, and by wiring ApprovalEngine session prefix grants as the pressure valve, but the social failure mode is not eliminated by code.
- The splitter becomes a correctness dependency in the security path. ## RATIONALE

I verified each named pair against its actual body rather than its name, and the groups split three ways.

Seven groups are textually identical code — `reverse_dns`/`osint_reverse_dns`, `robots_parser`/`web_robots_txt`, `subdomain_bruteforce`/`osint_subdomain_enum`, `dns_lookup`/`osint_dns_enum`, `http_header_analyzer`/`web_security_headers`, plus the two tech-fingerprint and two secret-scanner variants. These are the Tools_cyber plugin layer and the cyber_tools class layer having independently absorbed the same `ideas/` source. Merging them is free: same semantics, so no capability is lost, and the win is that the model stops choosing between two names for one action. Where the two differed I kept the superset and folded in the loser's one genuine improvement (ASP.NET header checks, URL normalisation, SHA-256 fingerprint, the lowercase-once optimisation) so no behaviour is dropped in the name of tidiness.

Four groups turned out to be a real implementation shadowed by a stub — `tls_cert_check`, `pe_header_analysis`, `import_table_scan`, `open_port_audit`. These are the highest-value deletions and the reason I did not treat this as cosmetic work: `{"status": "simulated", "cert_valid": True}` is not a duplicate of `tls_cert_inspect`, it is a tool that lies. A 50/50 name choice between the real tool and the stub is a coin-flip on whether the agent reports a certificate as valid without opening a socket. Collapsing them removes the coin-flip, which is worth more than the token savings.

I chose survivor names to minimise consumer churn rather than to be prettiest: `secret_scan` keeps its name with the Improved body because profiles.py and the benchmark both hardcode that string, whereas `improved_secret_scan` is referenced nowhere. Conversely I picked `web_robots_txt`/`web_tech_fingerprint` over the plugin names because they match the existing `web_*` family, and consumer greps came back empty for both.

I declined three merges the name list invited. `hash_identifier` classifies a hash string by regex and never opens a file — merging it with `sha256sum` would conflate "what kind of hash is this" with "hash this path." The two VirusTotal lookups hit different endpoints, are both named in profiles.py, and already have a polymorphic router in `enrich_artifact`. `file_tool` and `workspace_read_file` differ in risk level, which is load-bearing: one is auto-approved and the other prompts.

## RISKS

- Merging dns_lookup/nslookup/dig into the pure-Python resolver takes a hard dependency on dnspython. - Several merged tools change their return envelope. Tools_cyber plugins return {"success", "output", "error"} while cyber_tools python_funcs return a bare dict. Every merge that keeps the cyber_tools side (web_robots_txt, web_tech_fingerprint, web_security_headers, tls_cert_inspect, osint_subdomain_enum) silently changes the shape the model sees for that action, and any prompt, eval, or subagent definition that taught the old output.* nesting will read as broken until re-checked. I only grepped profiles.py for the 13 candidate groups, not for the 16 stub names.

Three findings drove the sequencing. (1) The AST-based tests in tests/test_tool_registry_consistency.py are the binding constraint: they scan cyber_agent.py for execute_tool("literal") and tools=/recommended_tools= list literals and cross-check against the LIVE registry, so the moment a name leaves the registry, 14 literal sites in cyber_agent.py turn the suite red. (2) The `assertGreater(len(self.live), 150)` floor at line 65 is not a survivable assertion: 207-59+1 = 149 fails, and even the keep-Defender variant (150) fails a strict `>`. (3) windows_defender_scan is the one name that cannot be deleted: cyber_os/tool_orchestrator.py:570 silently re-registers it over the cyber_tools.py:2265 wrapper (register_tool at cyber_tools.py:522 is a bare dict assignment, last-writer-wins), it is the ONLY one of the 59 with a real python_func implementation, and tool_orchestrator.py:1288 is the only path that turns a Defender detection into a critical finding by parsing result["threats_found"].
